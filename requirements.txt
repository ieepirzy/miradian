# Pinned to a major, not left open. Unpinned, the container resolved fastmcp 4.x /
# mcp 2.x while the tests ran against 3.x/1.x, and the two disagree in ways that
# build green and then misbehave at runtime:
#   * mcp 2.x renamed McpError to MCPError, so the image died on import.
#   * under fastmcp 4.x every ctx.elicit call raises, so the human-approval gate on
#     schema changes refuses unconditionally -- it fails closed, so nothing becomes
#     unsafe, but vault_create_tag and friends stop working entirely.
# Moving to 4.x is a deliberate port, not a resolver's choice. See design/unresolved.md.
fastmcp>=3.4,<4
mcp>=1.28,<2
origo>=0.3.0
ruamel.yaml>=0.18
starlette>=0.40
uvicorn[standard]>=0.30

# Transitive (httpx2, httpcore2, anyio), pinned only to set security floors: a
# bare ">=" range on our direct deps lets a resolver -- including OSV's scanner
# -- pick a vulnerable minimum, so state the floors explicitly rather than rely
# on luck.
# idna < 3.15 is vulnerable to GHSA-65pc-fj4g-8rjx.
idna>=3.15
# httpx2 < 2.12.0 is vulnerable to GHSA-7mj9-2mp8-4m2p, GHSA-8xx6-hgc6-gc2m,
# GHSA-f2fp-rgf2-35cp, GHSA-h4x7-gw46-3wm6, GHSA-pf96-p4fj-6566 (pulled in by
# fastmcp's [client]/[server] extras).
httpx2>=2.12.0
# httpcore2 < 2.10.0 is vulnerable to GHSA-7mj9-2mp8-4m2p (httpx2's own
# transitive dependency).
httpcore2>=2.10.0
